# Corch field notes

What the orchestrating chat ran into while using Corch on real work. Each note says what happened,
why it matters, and where it stands. Newest run first; a note is updated in place when it is fixed.

## Run 1, 2026-09-30: Connections mobile fixes (the owner's first real corch task)

Task: fix the phone layout of events.connections.icu (the Events list rows, the Guests tab's
"3 ahead" chip, its "Person" header and its tall "Check in" buttons), then sweep the rest of the
Connections site on a phone. Orchestrator: a desktop Opus 5.5 chat in the Connections repo.
Accounts signed in at start: #83, #84, #88, #90, #91, #94 (and #68, #69, which report signed in but
failed `auth` in earlier runs).

| 1 | `corch_status {}` with no filter returned every worker ever recorded (141 of them, 51k characters), which overflowed the tool result, so the call answered nothing useful. | The first call a new orchestrator makes is "what is running?", and it fails. | Fixed in 158ea61: with no group or id, `corch_status` answers every active worker plus the 20 most recently finished, newest first, brief (no prompt, last 3 attempts); `active` and `limit` parameters added. |
| 2 | There is no log of the orchestration as a whole. | 7 | `corch_run` echoes every worker's full view back, including 300 characters of each prompt, so a five-task dispatch returns about 3k characters the orchestrator already wrote. | Wasted context on every dispatch. | Fixed in 158ea61: `corch_run` answers only the group and each worker's id, title, status and account. |
| 8 | Eight workers over four dispatches landed two per account on #84, #88, #90 and #94, while #83 (week 49%) and #91 (week 20%) stayed idle. `per_account` and the `+25 per active` score count only the worker's own group, so different groups stack on the same account although a fresher one is free. | A heavy wave concentrates on four accounts and drains them together, instead of spreading over six. | Fixed in d47056e: the score adds 100 per worker already running on the account from ANY group (was 25, own group only); `per_account` stays a per-group cap. |

| 10 | `corch_send` to a RUNNING worker is held until its whole task ends (a `-p` session takes no input mid-run); only the answer ("Queued: the task gets it after it finishes its current work") says so. Needed live: the Corch worker's half-done edit broke AgentHydra's server type check and blocked another session's lands, and the "fix the build first" message could not reach it. | The skill says "steer with corch_send"; for anything urgent that does nothing until the task is over. | Fixed in bf9c3b5: `corch_send { urgent: true }` stops the running work cleanly and delivers the message first; a plain send says it is held; the view has "Stop and send now". |
| 11 | `corch_cancel` on a worker with three queued follow-ups dropped all three silently (`pending: 0` after the cancel). | Steering the orchestrator already sent is lost without a word. | Fixed in bf9c3b5: a cancel keeps queued messages (`keptMessages`) and delivers them, in order, when the worker is continued. |
| 12 | Workers edit a shared working tree, so one worker's half-finished edit fails a whole-tree gate (AgentHydra's land type check) for every other session in that repo until it finishes. | Parallel workers in a busy repo block peers who are not part of the run. | Fixed (claude-memory 6481be6): `cycle.py --land` judges the commit. Its test passes. |
| 13 | A worker's `result` holds only the text of its LAST turn. | 14 | `corch_wait.py` watches named groups only, so every new wave means stopping the waiter and starting another with the new group added (done three times in run 1). | Easy to miss a new wave's results; churn on every dispatch. | Fixed (claude-memory 4a76419): `--group` takes a trailing `*` as a prefix, resolved on every poll, so a wave dispatched after the waiter started is watched without a restart.
